## A. Fundamentos

### 1. Autenticação x autorização
A **autenticação** serve para descobrir quem é o usuário que está fazendo a requisição, validando o e-mail e a senha no `POST /auth/login` ou conferindo o token enviado no header [Authorization](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Authorization). Já a **autorização** vem logo depois e serve para checar o que esse usuário já identificado tem permissão para fazer dentro do sistema. Na nossa API de Chamados, a autenticação acontece no middleware `autenticar` quando a usuária Ana (`ana@chamados.com`) manda o token dela para abrir um chamado em `POST /chamados`. A autorização entra em ação quando o middleware `autorizar('ADMIN')` barra a Ana ao tentar listar todos os usuários em `GET /users`, ou quando ela tenta editar o chamado nº 3 que pertence ao Bruno. Quando a autenticação falha (sem token ou token inválido), a API retorna [401 Unauthorized](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/401) porque não sabemos quem é a pessoa; quando a autorização falha, retorna [403 Forbidden](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/403) porque sabemos quem é o usuário, mas o perfil dele não permite aquela ação.

### 2. Stateful x stateless
No login **stateful** (com estado, igual ao `$_SESSION` do PHP), o servidor guarda os dados da sessão na memória ou no banco e entrega apenas um ID de sessão em um cookie para o navegador, precisando consultar essa lista interna em toda requisição. No login **stateless** (sem estado, usando [JWT - RFC 7519](https://www.rfc-editor.org/info/rfc7519/)), o servidor não guarda nenhuma sessão aberta na memória: ele gera um token assinado com os dados básicos do usuário (`sub` e `role`) e o próprio cliente reenvia esse token a cada rota. A principal **vantagem do stateful** é poder cancelar a sessão de um usuário na hora (basta apagar a sessão no servidor), enquanto a **desvantagem** é gastar mais memória no servidor conforme o número de usuários cresce. No **stateless (JWT)**, a **vantagem** é que a API fica muito mais rápida e fácil de escalar (o middleware `autenticar` só confere a assinatura com a `JWT_SECRET`), e a **desvantagem** é que o token continua valendo até o tempo de expiração (`exp`) acabar, mesmo depois que o usuário sai da conta.

### 3. Hash x criptografia x encoding
O **encoding** (codificação, como o Base64URL) serve só para formatar dados em texto seguro para viajar na URL ou nos cabeçalhos HTTP, sem proteger nada com senha, então qualquer um consegue reverter. A **criptografia** (como AES ou RSA) embaralha os dados usando uma chave secreta e é um caminho de mão dupla, ou seja, quem tem a chave consegue descriptografar e ler a informação original. Já o **hash** (como SHA-256 ou [bcrypt](https://github.com/dcodeIO/bcrypt.js/)) é um cálculo matemático de mão única (irreversível): depois que o texto vira hash, não existe função que volte para a palavra original. No nosso projeto, usamos o **hash** (com `bcryptjs`) para salvar as senhas na tabela `User` do banco SQLite, e usamos o **encoding** (`Base64URL`) no `header` e no `payload` do [JWT](https://jwt.io/introduction), que é o motivo de qualquer pessoa conseguir colar o token no site jwt.io e ler os dados do payload.

### 4. bcrypt e salt
Algoritmos como MD5 e SHA-256 foram criados para serem muito rápidos, o que é péssimo para senhas porque uma placa de vídeo atual consegue testar bilhões de combinações por segundo em um ataque de força bruta se o banco vazar. O [bcrypt](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) é bem mais seguro para senhas porque ele é um algoritmo propositalmente lento, feito para gastar processamento a cada tentativa. O **custo** (como o número `10` que colocamos em `bcrypt.hash(password, 10)` no `authController.js`) define quantas rodadas internas o algoritmo vai rodar (2 elevado a 10, ou seja, 1.024 vezes), deixando o cálculo mais pesado. Já o **salt** é um texto aleatório que o próprio `bcryptjs` cria e mistura na senha antes de gerar o hash: graças a ele, mesmo que a Ana e o Bruno usem a mesma senha (`123456`), os hashes salvos no banco ficam totalmente diferentes, protegendo contra tabelas prontas (*rainbow tables*).

## B. JWT

### 5. Estrutura
De acordo com a [documentação do jwt.io](https://jwt.io/introduction) e a [RFC 7519](https://www.rfc-editor.org/info/rfc7519/), o token JWT é dividido em três partes separadas por ponto (`header.payload.signature`). O **Header** guarda o tipo do token (`JWT`) e o algoritmo usado na assinatura (`HS256`), o **Payload** guarda os dados (*claims*) do usuário logado e a validade, e a **Signature** é a assinatura gerada juntando o header, o payload e a nossa chave `JWT_SECRET` no algoritmo HMAC-SHA256. Abaixo está um token real gerado ao fazer login com a usuária Ana (`id: 2`, `role: "USER"`) na nossa API de Chamados e decodificado no [jwt.io](https://jwt.io/):

- **Token gerado pela API:** `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOjIsInJvbGUiOiJVU0VSIiwiaWF0IjoxNzYyNjg3ODAwLCJleHAiOjE3NjI2OTUwMDB9.JQrIL1RfFIdlX4HvPndKikiM7MqkbM7VtAOtklyceL0`
- **Header decodificado:** `{"alg": "HS256", "typ": "JWT"}`
- **Payload decodificado:** `{"sub": 2, "role": "USER", "iat": 1762687800, "exp": 1762695000}`

### 6. Claims
Pelo padrão da [RFC 7519](https://www.rfc-editor.org/info/rfc7519/), as claims registradas têm nomes curtos de três letras: **`sub`** (*Subject*) guarda o identificador de quem é o dono do token (no nosso projeto, o `id` do usuário no banco), **`iat`** (*Issued At*) marca a data e hora (em segundos Unix) em que o token foi criado, e **`exp`** (*Expiration Time*) marca a data e hora em que o token vence e para de ser aceito. Na nossa API de Chamados de Suporte, colocamos no payload apenas o `sub` (para pegar o dono do chamado em `req.usuario.id`) e o `role` (para o middleware `autorizar` saber se é `USER` ou `ADMIN`), além do `iat` e `exp` criados pelo `expiresIn`. **Não devemos colocar no payload** informações sensíveis como senha, hash de senha, CPF ou chaves privadas, porque o payload está apenas em Base64URL e pode ser lido por qualquer um sem precisar da chave secreta.

### 7. Assinatura
Se um usuário comum abrir o token dele no jwt.io, mudar o payload de `"role": "USER"` para `"role": "ADMIN"` para tentar fechar chamados ou acessar `GET /users`, ele **não vai conseguir gerar a assinatura certa** porque ele não tem a chave `JWT_SECRET` que fica guardada só no servidor. Quando ele mandar esse token modificado para a API, o servidor vai refazer o cálculo da assinatura usando o payload alterado e a `JWT_SECRET` verdadeira; como o resultado vai dar diferente da assinatura que veio no token, a requisição é bloqueada na hora com erro `401`. Essa é a diferença entre as duas funções do pacote [jsonwebtoken](https://github.com/auth0/node-jsonwebtoken): o `jwt.decode()` só traduz o Base64URL do payload para JSON **sem conferir se a assinatura é verdadeira** (aceitaria qualquer token editado), enquanto o `jwt.verify()` confere a assinatura com a `JWT_SECRET` e checa se o tempo `exp` não expirou.

### 8. Validade e logout
Como o JWT não fica salvo em uma sessão no servidor, quando o usuário clica em sair (logout) ou quando um `ADMIN` muda o perfil dele em `PATCH /users/:id/role`, o token antigo que já tinha sido emitido **continua valendo até o horário de expiração (`exp`) acabar**. Por isso, se um usuário for promovido a `ADMIN`, ele precisa fazer login de novo em `POST /auth/login` para receber um token novo com `"role": "ADMIN"`. Para resolver isso em sistemas maiores, o [guia de JWT da OWASP](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html) recomenda usar **Refresh Token**: a API entrega um *Access Token* bem curto (por exemplo, de 10 ou 15 minutos) para usar nas rotas normais e um *Refresh Token* mais longo salvo no banco de dados. Quando o token curto vence, o front-end pede outro usando o *Refresh Token*; se o usuário fizer logout ou mudar de perfil, basta apagar o *Refresh Token* do banco que ele não consegue mais renovar o acesso.

## C. Segurança na prática

### 9. Onde guardar o token
No front-end, salvar o token no **`localStorage`** é o jeito mais prático para estudar (basta salvar no login e ler na hora de montar o header `Authorization: Bearer`), mas tem o risco de **XSS (*Cross-Site Scripting*)**: se alguém conseguir injetar um código JavaScript malicioso na página, esse script consegue ler o `localStorage` e roubar o token do usuário. Já salvar o token em um **cookie `HttpOnly`** (enviado pelo servidor no cabeçalho [Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie) com as opções `HttpOnly` e `Secure`) impede que qualquer script acesse o token via `document.cookie`, protegendo contra XSS. Por outro lado, como o navegador manda os cookies automaticamente em toda requisição para aquele site, surge o risco de **CSRF (*Cross-Site Request Forgery*)**, que é quando uma página externa engana o navegador do usuário logado e dispara uma ação na API sem ele perceber.

### 10. Chave secreta
A chave `JWT_SECRET` fica dentro do arquivo `.env` (que colocamos no `.gitignore`) para que o segredo usado para assinar os tokens nunca vá parar no repositório público do GitHub. No GitHub enviamos apenas o arquivo `.env.example`, que mostra quais variáveis o projeto precisa para rodar, mas sem a chave de produção. Se a `JWT_SECRET` real vazasse no GitHub, qualquer pessoa poderia copiar essa chave e usar o `jwt.sign()` no próprio computador para **fabricar tokens falsos** com `{"sub": 1, "role": "ADMIN"}`. Como a assinatura seria gerada com a chave certa do servidor, o `jwt.verify()` do nosso middleware `autenticar` acharia que o token é legítimo, e o invasor conseguiria apagar chamados, ver todos os usuários e controlar a API inteira sem precisar saber a senha de ninguém.

### 11. RBAC e dono do recurso
O controle por perfil (**RBAC**) libera ou bloqueia o acesso olhando apenas para o cargo do usuário (`USER` ou `ADMIN`), enquanto a **regra do dono** olha para quem criou aquele item específico no banco (`chamado.usuarioId === req.usuario.id`). No nosso código, o **RBAC** está no arquivo `src/middlewares/autorizar.js`, que usamos nas rotas `GET /users` e `PATCH /users/:id/role` (`src/routes/userRoutes.js`) passando `autorizar('ADMIN')`, e também no `GET /chamados`, onde o `ADMIN` recebe todos os chamados e o `USER` recebe só os que ele mesmo abriu. Já a **regra do dono** fica em `src/controllers/chamadoController.js`: ao abrir um chamado (`POST /chamados`), gravamos o `usuarioId` pegando direto de `req.usuario.id` (do token) e ignorando o `req.body`; e nas rotas `PUT /chamados/:id` e `DELETE /chamados/:id`, primeiro buscamos o chamado para retornar `404` se não existir e depois retornamos `403` se `chamado.usuarioId !== req.usuario.id && req.usuario.role !== 'ADMIN'`.

### 12. OWASP
Pesquisando no [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) e no [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) (que detalham os cuidados do item [A07 do OWASP Top 10](https://top10.owasp.org/2021/A07_2021-Identification_and_Authentication_Failures/)), escolhemos duas recomendações diretas sobre login e senhas:
1. **Mensagens de erro genéricas no login:** A OWASP orienta a nunca avisar no login se foi o e-mail que não foi encontrado ou se foi só a senha que estava errada, para evitar que alguém descubra quais e-mails estão cadastrados. **O nosso projeto segue isso** no `src/controllers/authController.js`: tanto quando o e-mail não existe quanto quando a senha não bate no `bcrypt.compare`, devolvemos status `401` com a mesma frase `"E-mail ou senha inválidos."`.
2. **Hash lento com salt para senhas e ocultação na saída:** A OWASP recomenda guardar senhas sempre com algoritmos lentos como bcrypt ou Argon2 e nunca devolver o hash nas respostas. **O nosso projeto segue isso** usando `bcrypt.hash(password, 10)` no cadastro e configurando `omit: { password: true }` do [Prisma ORM 7](https://www.prisma.io/docs/orm/v7/prisma-client/queries/excluding-fields) nas consultas de usuário.
